## 1. Protocol pin and regeneration

- Pin: `scripts/package.json` -> `"@dcl/protocol": "^1.0.0-37324405267.commit-d7ddc10"` (equals npm dist-tag `next` today). The repo tracks protocol `main` via `@next` since `chore: migrate to 'main' protocol (#10060)`; before that it tracked `@experimental`. Every feature PR that needs new proto bumps this pin itself and commits `scripts/package-lock.json` plus the regenerated files.
- Regenerate (run from the repo root):

  ```bash
  cd scripts && npm install @dcl/protocol@next && npm run build-protocol   # published build
  make upgrade-protocol-by-url URL="https://.../dcl-protocol-1.0.0-<hash>.tgz" # PR bot tarball
  make regenerate-protocol                                                 # npm install + build-protocol
  ```

  Avoid `make upgrade-protocol`: it still installs `@dcl/protocol@experimental`, a tag that lags `main` and misses components.
- `scripts/src/build-protocol.ts` copies `node_modules/@dcl/protocol/proto` to `scripts/temp`, strips every `option (common.ecs_component_id)` line (regex `/option *\(common.ecs_component_id\) *= *([0-9]+) *;/`) and the `common/id.proto` import, appends `option csharp_namespace = "DCL.ECSComponents";`, skips `id.proto` and `comms/v1|v2|v3/comms.proto`, then runs protoc with `--csharp_out`, `--csharp_opt=file_extension=.gen.cs` and the `protoc-gen-bitwise` Node plugin shipped inside the npm package, and copies `Quantize.cs`.
- Output (committed, header `/* Autogenerated file, DO NOT EDIT! */`): `Explorer/Assets/Protocol/DecentralandProtocol/*.gen.cs`, `*.Bitwise.cs`, `Quantize.cs`, `ComponentID.gen.cs`, all inside `Decentraland.Protocol.GeneratedCode.asmdef`. Message classes live in namespace `DCL.ECSComponents`; ids in `DCL.ECS7.ComponentID`.
- ComponentID naming rule (`scripts/src/helpers.ts:camelToSnakeCase` + `.toUpperCase()` on the proto file stem): `avatar_shape.proto` -> `public const int AVATAR_SHAPE = 1080;`, `avatar_nametag.proto` -> `AVATAR_NAMETAG = 1221`. The constant name comes from the file name, not the message name, so name the file the way you want the C# constant to read. Highest on `dev` today: `EXPLORER_ITEM_PURCHASE_RESULT = 1222`.
- Review check: `scripts/package.json`, `scripts/package-lock.json` and `*.gen.cs` must agree and point at a published `@next` build before merge, because both precedents drifted (#9902 regenerated `PointerEvents.gen.cs` while "package.json still pins the older npm release"; #9829 merged pinned to an experimental build of protocol#467).

## 2. New SDK component: registration shapes

Precedent: `feat: sdk | scene name tag (#9829)` (AvatarNametag, id 1221, protocol#467). Seven touch points:

1. `Explorer/Assets/DCL/Infrastructure/ProtobufPartialClasses/IDirtyMarker.cs` (namespace `DCL.ECSComponents`), required because `AsProtobufComponent<T>` is constrained `where T: class, IMessage<T>, IDirtyMarker, new()` and its pool `onGet` sets the flag and clears the message:

   ```csharp
   public partial class PBAvatarNametag : IDirtyMarker
   {
       public bool IsDirty { get; set; }
   }
   ```

2. `Explorer/Assets/DCL/Infrastructure/Global/ComponentsContainer.cs`, the `SDKComponentsRegistry` chain:

   ```csharp
   .Add(SDKComponentBuilder<PBAvatarNametag>.Create(ComponentID.AVATAR_NAMETAG).AsProtobufComponent())
   .Add(SDKComponentBuilder<PBExplorerUiEventsResult>.Create(ComponentID.EXPLORER_UI_EVENTS_RESULT).AsProtobufResult())
   ```

   `AsProtobufResult()` is for engine-written results (grow-only or LWW written with PUT/APPEND by a system) and needs no `IDirtyMarker` partial.
3. Feature folder `Explorer/Assets/DCL/SDKComponents/<Feature>/{Systems,Tests}` with two asmref files so the code compiles into the existing assemblies:

   ```json
   // Systems/<Feature>.Systems.asmref  -> Explorer/Assets/DCL/PluginSystem/DCL.Plugins.asmdef
   { "reference": "GUID:fc4fd35fb877e904d8cedee73b2256f6" }
   // Tests/<Feature>.Tests.asmref      -> Explorer/Assets/DCL/Tests/Editor/DCL.EditMode.Tests.asmdef
   { "reference": "GUID:da80994a355e49d5b84f91c0a84a721f" }
   ```

4. A world plugin. The real interface (`Explorer/Assets/DCL/PluginSystem/World/IDCLWorldPlugin.cs`) takes six parameters; implement `IDCLWorldPluginWithoutSettings` when there are no exposed settings:

   ```csharp
   void InjectToWorld(ref ArchSystemsWorldBuilder<Arch.Core.World> builder,
       in ECSWorldInstanceSharedDependencies sharedDependencies,
       in SystemsDependencies systemsDependencies,
       in PersistentEntities persistentEntities,
       List<IFinalizeWorldSystem> finalizeWorldSystems, List<ISceneIsCurrentListener> sceneIsCurrentListeners);
   ```

   Current example `Explorer/Assets/DCL/PluginSystem/World/AvatarNametagWorldPlugin.cs`: injects `PropagateSceneAvatarTagSystem.InjectToWorld(ref builder, sharedDependencies.SceneStateProvider, entityParticipantTable, globalWorld, globalPlayerEntity)` and adds it to both `sceneIsCurrentListeners` and `finalizeWorldSystems`. Add `ResetDirtyFlagSystem<PBX>.InjectToWorld(ref builder);` (`Explorer/Assets/DCL/Infrastructure/ECS/LifeCycle/Systems/ResetDirtyFlagSystem.cs`) so `IsDirty` clears after your systems ran, as `AvatarShapePlugin` does. Location is inconsistent and both compile: `docs/how-to-implement-new-sdk-components.md` and AvatarNametag/AvatarShape/LightSource/Tween use `Explorer/Assets/DCL/PluginSystem/World/<Feature>Plugin.cs`; the `sdk-component-implementation` skill, ParticleSystem and SDKExternalPhysics (folder `PhysicsImpulse/`) use `Explorer/Assets/DCL/SDKComponents/<Feature>/Systems/<Feature>Plugin.cs`. Match the neighbour you copy from.
5. Register the plugin in one of two lists: `Explorer/Assets/DCL/Infrastructure/Global/StaticContainer.cs` `container.ECSWorldPlugins = new IDCLWorldPlugin[] { ... }` (~286) for scene-world plugins, or `Explorer/Assets/DCL/Infrastructure/Global/Dynamic/DynamicWorldContainer.cs` `var worldPlugins = new List<IDCLWorldPlugin> { ... }` (~440) when the plugin needs comms or multiplayer services that only exist there (`commsContainer.EntityParticipantTable`, the emotes message bus): `AvatarAttachPlugin`, `SceneMaskedEmotePlugin`, `new AvatarNametagWorldPlugin(globalWorld, playerEntity, commsContainer.EntityParticipantTable)`.
6. Systems in the feature folder (nametag: `PropagateSceneAvatarTagSystem.cs`), plus any global-world rendering code (nametag: `Explorer/Assets/DCL/NameTags/*`).
7. EditMode tests `<System>Should.cs` on `UnitySystemTestBase<TSystem>` (`Explorer/Assets/DCL/Infrastructure/ECS/TestSuite/UnitySystemTestBase.cs`, NUnit + NSubstitute).

LWW vs grow-only, PUT vs APPEND and cleanup rules: `docs/how-to-implement-new-sdk-components.md` (ADR-117), with `Explorer/Assets/DCL/Infrastructure/ECS/Unity/EngineInfo/WriteEngineInfoSystem.cs` as the LWW writer and `Explorer/Assets/DCL/SDKComponents/MediaStream/Systems/VideoEventsSystem.cs` as the grow-only writer.

## 3. New field on an existing component

No `ComponentsContainer`, `IDirtyMarker` or plugin change; the PR is the pin bump, the regenerated `.gen.cs`, the reader and a test:

- `feat: sdk virtual camera FOV (#3487)`: `Explorer/Assets/DCL/SDKComponents/CameraControl/MainCamera/VirtualCameraUtils.cs:ConfigureVirtualCameraFOV` (`if (!pbVirtualCamera.HasFov) return;`), `MainCamera/Systems/MainCameraSystem.cs`, `MainCamera/Tests/EditMode/VirtualCameraUtilsShould.cs`, `VirtualCamera.gen.cs`, `scripts/package.json`, `scripts/package-lock.json`.
- `feat: pointerEvents component maxCameraDistance (#9902)` (protocol#470, cross-linked to js-sdk-toolchain#1560 and bevy-explorer#1158): `Explorer/Assets/DCL/Interaction/PlayerOriginated/Utility/InteractionInputUtils.cs` (`float? maxCameraDistance = info.HasMaxCameraDistance ? info.MaxCameraDistance : null;`), `PlayerOriginated/Tests/InteractionInputUtilsShould.cs`, `Explorer/Assets/DCL/Interaction/Systems/{PlayerOriginatedProximitySystem,PlayerOriginatedRaycastSystem}.cs`.

Proto3 presence pitfall (from the #9902 body): the generated setters flip the `Has*` presence bits, so writing defaults onto the live message ("`PrepareDefaultValues` wrote `MaxDistance = 10` / `MaxPlayerDistance = 0`") made every entry look like both fields were set and left a branch dead. Resolve defaults at read time (`HasX ? X : default`) and do not write them back into the PB.

## 4. Being in ComponentID.gen.cs is not support

The generator emits a constant and a class for every proto in the package, so presence in `ComponentID.gen.cs` only proves the pin. On `dev`, `TOUCH_SCREEN_CONTROLS = 1218`, `UI_INPUT_BINDING = 1219` and `EXPLORER_ITEM_PURCHASE_RESULT = 1222` exist, yet no file under `Explorer/Assets/DCL` references `PBTouchScreenControls`, `PBUiInputBinding` or `PBExplorerItemPurchaseResult`; `PBAvatarShape.Talking` (field 9) and `.Emotes` (field 11) are never read. Prove a consumer before claiming support:

```bash
git grep -l "PB<Name>" origin/dev -- 'Explorer/Assets/DCL'            # registration + readers
git grep -n -E "\.<Field>\b|Has<Field>" origin/dev -- 'Explorer/Assets/DCL'
```

## 5. Restricted actions: four hand-written layers

Kernel APIs (`proto/decentraland/kernel/apis/*.proto`) are not generated into JS bindings; only the message classes are regenerated. A scene's `require('~system/RestrictedActions')` travels through:

1. `Explorer/Assets/StreamingAssets/Js/Modules/RestrictedActions.js`, hand-mirrored against `restricted_actions.proto` (its header links the file). Optional fields are unpacked by hand and passed positionally: `message.realm != undefined ? message.realm : null`; enums exposed to scenes are `makeEnum([...])` tables.
2. `Explorer/Assets/DCL/Infrastructure/SceneRuntime/Apis/Modules/RestrictedActionsApi/RestrictedActionsAPIWrapper.cs`: `[UsedImplicitly]` public methods; async ones return `...Async(ct).ToDisconnectedPromise(this)`.
3. `.../RestrictedActionsApi/IRestrictedActionsAPI.cs`: `TryTeleportTo`, `TryTriggerEmote`, `TryTriggerSceneEmoteAsync`, `TryStopEmote`, ...
4. `Explorer/Assets/DCL/Infrastructure/CrdtEcsBridge/JsModulesImplementation/RestrictedActions/RestrictedActionsAPIImplementation.cs`: guards with `if (!sceneStateProvider.IsCurrent)` and delegates to `IGlobalWorldActions`; tests in the sibling `Tests/` folder (`RestrictedActionsAPIImplementationShould.cs`).

Registration: `Explorer/Assets/DCL/Infrastructure/SceneRuntime/ISceneRuntime.cs` ~200: `sceneRuntime.Register("UnityRestrictedActionsApi", new RestrictedActionsAPIWrapper(api, sceneRuntime.isDisposingTokenSource));`. Precedent `feat: sdk teleportTo realm coords support (#10047)` touched the JS module, the wrapper, the interface, the implementation and its test, `UserActionsWrapper.cs`, the pin and lockfile, plus the `PulseClusters.gen.cs` (+ `.meta`) that the regeneration pulled in.

## 6. AvatarShape: locomotion versus emote path

- `Explorer/Assets/DCL/SDKComponents/AvatarShape/Systems/AvatarShapeHandlerSystem.cs` (scene world, `[UpdateInGroup(typeof(ComponentInstantiationGroup))]`, `[ThrottlingEnabled]`) creates a global-world twin with `globalWorld.Create(pbAvatarShape, ...)` and on `IsDirty` does `globalWorld.Set(sdkAvatarShapeComponent.GlobalWorldEntity, pbAvatarShape)`, so a new `PBAvatarShape` field is readable from global-world systems with no new registration. It turns `ExpressionTriggerId`/`ExpressionTriggerTimestamp` into emote intents with `loop: false` hard-coded ("looping scene emotes on SDK AvatarShapes is not supported yet"). Every `IsDirty` re-runs this, so a scene calling `getMutable` each frame keeps it permanently dirty.
- `.../AvatarShape/Systems/UpdateAvatarShapeInterpolateMovementSystem.cs` (`SyncedSimulationSystemGroup`, after `UpdateTransformSystem`) copies the scene transform into `CharacterInterpolationMovementComponent.TargetPosition/TargetRotation` and sets `IsPositionManagedByTween`/`IsRotationManagedByTween`.
- `Explorer/Assets/DCL/Character/CharacterMotion/Systems/SDKAvatarShapesMotionSystem.cs` (global world, `PresentationSystemGroup`, query `[All(typeof(PBAvatarShape))]`, injected by `Explorer/Assets/DCL/PluginSystem/Global/CharacterMotionPlugin.cs` ~151): interpolates at `WALK_SPEED = 4f` / `RUN_SPEED = 10f`, slerps rotation toward the move direction, and `UpdateAnimations` sets `MovementBlend` from `RemotePlayerUtils.GetBlendValueFromSpeed(distance / deltaTime)` via `AnimationMovementBlendLogic.SetAnimatorParameters` (`AnimationHashes.MOVEMENT_BLEND`). Tween-managed moves skip the position interpolation but the blend is still computed from `TargetPosition` vs `LastPosition`. This is the hook for any "keep emote while moving" flag.
- `Explorer/Assets/DCL/AvatarRendering/AvatarShape/Assets/Animator/CharacterAnimator.controller` (ASCII YAML): state `Emote` (tag `Emote`) owns a transition to `Movement` conditioned `MovementBlend Greater 0.1` with `m_HasExitTime: 0`, but it carries `m_Mute: 1` on `dev` (its `IsFalling` -> `Down` exit is muted as well), and muted transitions do not fire; `Emote Loop` (tag `EmoteLoop`) owns the same muted `MovementBlend Greater 0.1` -> `Movement` transition and a muted `IsFalling` -> `Down` (verified 2026-10-10 by parsing the controller YAML). The live exits are the `EmoteStop` trigger (from both states), the `EmoteRefresh` trigger and the `EmoteLoop`-false transitions at exit time.
- `Explorer/Assets/DCL/AvatarRendering/Emotes/Systems/Play/CharacterEmoteSystem.cs`: `CancelEmotes` stops with `EsFinished` only when the animator leaves the Emote/EmoteLoop tags (or `EsInterrupted` on `StopEmote`/`HiddenPlayerComponent`); `CancelEmotesByMovementInput` requires `JumpInputComponent`, `MovementInputComponent` and `Profile`, so it covers the local player only (its comment cites issues #6246/#4306: cancel on input, not physics velocity); `CancelEmotesByMoveToWithDuration` needs `PlayerMoveToWithDurationIntent`. `StopEmote` records `PendingStop` for `AvatarEmoteCommand`.
- Verdict for a Transform-moved NPC playing an emote: no code path cancels it and the animator transition that would is muted, so Unity may already keep the emote; treat it as `uncertain` until observed at runtime (section 8), because legacy-animation emotes (local scene dev with raw GLBs, `emoteReference.legacy`) bypass Mecanim and the Mecanim path has not been observed with a moving NPC. SDK AvatarShapes are local-only NPCs with no network replication.

## 7. What agents cannot do

- Compile or run Unity: `make test-editmode TEST_FILTER=...` / `make test-playmode` need the Editor at `/Applications/Unity/Hub/Editor/$(UNITY_VERSION)/...` with `UNITY_VERSION` read from `Explorer/ProjectSettings/ProjectVersion.txt` (`6000.5.9f1` today); CI `.github/workflows/test.yml` runs both modes on PRs. The agent-side gate is `cd scripts && npm run build-protocol` succeeding; C# correctness stays a human/CI check.
- Create `.meta` files: a new `.gen.cs` needs its Unity-generated `.meta` committed (#10060 added `ExplorerItemPurchaseResult.gen.cs.meta`), which only appears after the Editor imports the asset. List new files for the human to import.
- Skip the lint hook: `.claude/settings.json` runs `bash scripts/lint/lint-changed.sh` (ReSharper InspectCode on changed `.cs`, as CI does) on Stop.

## 8. Runtime verification

- Human QA: `metaforge explorer run <PR>` (`--clear` wipes Explorer data; `metaforge account create --clear` for a fresh account; `metaforge explorer logs tail --filter "<text>"`; `metaforge explorer test <PR>` for automation) against the ZONE/SEPOLIA world `sdk7testscenes.dcl.eth` at the scene's parcel (test-scene side in `.claude/skills/protocol-feature/references/repos/verification.md`).
- Local scene: in the scene folder `npm i` then `npm run start -- --explorer-alpha` (`docs/how-to-connect-to-a-local-scene.md`; Editor: Main Scene Loader -> Initial Realm `Localhost`; custom build `open Decentraland.app --args --realm http://127.0.0.1:8000 --position 0,0 --local-scene true --debug --skip-version-check true`).
- Agent-driven: `npm run start -- --mcp` starts the client with its embedded MCP server at `http://127.0.0.1:8123/unity-explorer-mcp` (`Explorer/Assets/DCL/McpServer/Systems/McpServerPlugin.cs` `DEFAULT_PORT = 8123`, `--mcp-port` overrides); `.claude/agents/mcp-server-engineer.md` documents the curl shape and tools (screenshots, movement, scene state). The `mcp-scene-iteration` skill the maps cite is on a feature branch only, not on `origin/dev`, so do not rely on it by name.

## 9. PR conventions

- Branch off `dev` with `feat/` `fix/` `chore/` `opti/` (`docs/branch-and-pr-standards.md`); title `type: description`, enforced by `.github/workflows/validate-pr-title.yml` (`pull_request_target` on base `dev`, `decentraland/actions` semantic check). Observed SDK titles: `feat: sdk | scene name tag`, `feat: sdk virtual camera FOV`, `feat: pointerEvents component maxCameraDistance`.
- Body follows `.github/PULL_REQUEST_TEMPLATE.md`: `## What does this PR change?` (link the protocol, js-sdk-toolchain and bevy PRs, e.g. "Implements decentraland/protocol#470"), `## Test Instructions` with `metaforge explorer run XXXX` steps and expected results, `## Quality Checklist` including `- [ ] For SDK features: Test scene is included`. SDK PRs end with the QA block, verbatim shape from #9902:

  ```markdown
  ### QA TEST STEPS

  Use the build from this PR to enter the ZONE/SEPOLIA world `sdk7testscenes.dcl.eth` at position `34,20` and confirm that ...
  ```

- Review flow: 1 QA + 1 DEV reviewer auto-assigned (`CODEOWNERS`: `* @decentraland/QA @decentraland/explorer-devs`); Jarvis AI review via `decentraland-bot` (feat/opti PRs never auto-approve); `Enforce QA and DEV Approvals` gates merge; use Squash and merge. The repo's `github-workflow` skill refuses to open a PR without reading the template and with partial info, so have the body ready before `gh pr create --title "feat: sdk | <thing>" --body "$(cat <<'EOF' ... EOF)"`.

## 10. Existing agents in the repo

`.claude/agents/dcl-sdk-feature-implementation/`: `README.md`, `dcl-sdk-feature-architect.md` (orchestrator, `skills: [sdk-component-implementation, github-workflow]`), `dcl-protocol-specialist.md` (haiku), `dcl-sdk-specialist.md` (sonnet), `dcl-explorer-specialist.md`, `dcl-test-scene-specialist.md` (sonnet). They cover definition -> implementation -> cross-layer check for Unity only; there is no need phase and no bevy/godot feasibility step.

- Invoke from the unity-explorer root with a `feature-description.md` at that root (README template headings: `# Feature: <Name>`, `## Overview`, `## Components` with one `### PBYourComponent (LWW — scene writes, Explorer reads)` block per component listing proto field lines, defaults and `Component ID: <n>`, `## Behavior`, `## Reference Components`):

  ```bash
  claude --agent dcl-sdk-feature-architect --permission-mode plan
  # then: Read @feature-description.md and create a plan to implement that DCL SDK feature.
  ```

  An inline `@dcl-sdk-feature-architect` mention does not work for orchestrators (README). In this skill's plan mode draft `feature-description-unity.md` inside the bundle and print `cp <bundle>/feature-description-unity.md <unity>/feature-description.md && cd <unity> && claude --agent dcl-sdk-feature-architect --permission-mode plan`; only execute mode writes into the unity repo.
- Assumptions to check before handing off: repos are siblings (`../protocol`, `../js-sdk-toolchain`, `../sdk7-test-scenes`; pre-flight asks the user to confirm paths, one branch name and the linking strategy); Option A links local paths (`cd scripts && npm install ../protocol && npm run build-protocol`), Option B uses the bot tarballs `https://sdk-team-cdn.decentraland.org/@dcl/protocol/branch/<branch>/dcl-protocol-1.0.0-<hash>.tgz`; every agent says it never commits or pushes; merge order is protocol first, then re-pin downstream to published `@next`, then SDK + Explorer, test scene last; the Unity play test "is the only step that requires human eyes".
- Stale snippets to override: the explorer specialist's plugin example `InjectToWorld(ref ArchSystemsWorldBuilder<Arch.Core.World> builder, params IFinalizeWorldSystem[] finalizeWorldSystems)` (real signature in section 2); the architect's and test-scene specialist's `npm install ../../js-sdk-toolchain/packages/@dcl/sdk` run from `scenes/<x>,<y>-<name>` resolves inside sdk7-test-scenes, so it needs `../../../`; README step 5 `npm run start --explorer-alpha` is missing the `--`; the test-scene specialist's `dcl-workspace.json` edits target a file that no longer exists on sdk7-test-scenes `main`; the protocol specialist's `make list-components-ids` / `make check-component-id ID=` only scan the local tree, so run the cross-branch id check from `.claude/skills/protocol-feature/references/repos/protocol.md` as well.
